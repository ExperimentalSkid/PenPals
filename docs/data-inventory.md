## Export exclusions

Exports never include passwords, password hashes, access/refresh tokens, service credentials, other users' private profile fields, reporter identities, or raw moderator-only evidence. Shared message content is included because it is part of the requesting user's communication history, while counterpart identity is reduced to `self`/`other`; messages whose sender account was deleted are labelled `Deleted user`.

## Deactivation versus deletion

Deactivation sets the profile inactive and prevents discovery/contact while preserving data for reactivation. Deletion permanently removes the authentication account, profile, owned selections, user-owned interactions, notifications, photo permissions, blocks, profile links, usernames, presence, and other live identity fields. Shared conversations survive for other participants with deleted senders anonymized as `Deleted user`; only orphaned conversations are removed. Avatar paths are queued and cleaned after commit.

Voluntary pause (`profiles.inactive_mode`) is a distinct, reversible participation state. It preserves the account and existing conversations, removes the user from discovery and new contact, suppresses presence, and freezes rank score with no earning, decay, or active-tenure accumulation. It does not set or reuse `deactivated_at`.

## Retention decisions still required

The application does not invent a new legal retention period. An administrator must explicitly configure `data_retention_policies` with a period, purpose, legal basis, and enabled state before moderation reports/evidence/audit rows are retained or purged. Case-specific `data_retention_holds` can pause purge and are released explicitly. Supabase `auth.audit_log_entries` is provider-managed; the application records that limitation but does not delete provider audit rows. A controller must decide the actual periods and provider retention settings.
